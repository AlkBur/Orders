# RFC-015: Entity Descriptor

## Status

Draft — after Commit 15 implementation (Products pilot).

## Problem

Все справочники (Customers, Organizations, Products, Warehouses, Employees,
Suppliers) имеют:

- одинаковую структуру списка (таблица + заголовок + поиск + кнопка создания);
- одинаковые подписи полей (label), необходимость перечислить поля на форме;
- одинаковые операции (List, Get, Save, Delete, Synchronize).

Но SQL, карточки и бизнес-логика — разные.

Цель: найти баланс между повторным использованием кода и избеганием
"умной" генерации, которая усложняет отладку.

## Решение

Введён пакет `internal/entity`, который описывает модель один раз (через
struct tags) и предоставляет метаданные для UI. SQL и карточки остаются
полностью ручными.

```go
type Field struct {
    GoName   string // Go field name
    DBName   string // из тега `db` (пустая у readonly полей)
    Label    string // из тега `label`
    Order    int    // из тега `order`
    List     bool   // из тега `list:"true"`
    Search   bool   // из тега `search:"true"`
    ReadOnly bool   // из тега `readonly:"true"`
}
```

Поля с `ReadOnly = true` не участвуют в Save(), не имеют `DBName` и
существуют только для отображения в UI (например, `OrganizationName`,
получаемое через JOIN).

API:

- `entity.Register[T]()` — регистрация модели (generics, reflection один раз, потокобезопасно)
- `Descriptor.ListFields()` — поля для списка, сортированные по Order
- `Descriptor.SearchFields()` — поля для поиска

## Структура проекта

```
internal/entity/          — описание моделей (только UI, не SQL)
internal/products/        — пилотный модуль на новой инфраструктуре
  model.go                — struct + entity.Register[Product]()
  store.go                — SQL полностью ручной
  ...
internal/customers/       — старая реализация (без entity)
internal/organizations/   — старая реализация (без entity)
internal/app/templates/list.html  — общий шаблон списка
internal/app/templates/product_card.html — индивидуальная карточка
```

## Что получилось удачно

1. **Один источник правды о полях модели.** Подписи, порядок колонок,
   состав списка и поиска описываются в struct tags один раз.

2. **Общий шаблон списка.** Убрал дублирование HTML между справочниками.
   `ListPage` достаточно гибок для текущих нужд.

3. **Reflection только при старте.** `Register[T]()` вызывается один раз
   при инициализации пакета, кеширует результат. В handler'ах и шаблонах
   reflection нет.

4. **Никакой генерации SQL.** Store пишет запросы явно. JOIN, WHERE,
   подзапросы — без ограничений. Код читается и отлаживается так же,
   как без entity.

5. **Индивидуальные карточки.** Карточка Product может отличаться от
   карточки Customer без «условной» логики в общем шаблоне.

6. **Products — пилот.** Если архитектура не понравится, переделываем
   только Products, не трогая Customers и Organizations.

## Что не понравилось / требует внимания

1. **Нет автоматизации карточек.** Пока ок, но когда справочников станет
   10+, ручная карточка для каждого — копипаста заголовка, label, input,
   checkbox.

2. **RowAction только один.** Сейчас у всех справочников одно действие
   («Открыть»). Когда появится второе («Удалить», «Копировать»), придётся
   расширять `ListPage` или `Row`.

3. **DisplayValue на модели.** Модель реализует `display.Values` —
   метод `DisplayValue(name string) (string, error)` для форматирования
   значений полей. Это ручная работа, но без импорта пакета отображения
   из домена (Go implicit interface). `BuildRows` пока не вынесен в общий
   код — отложен до появления второго модуля на entity.

## Почему не стали автоматизировать больше

### SQL остался ручным

Причина: SQL специфичен. Почти каждый запрос содержит:

- JOIN с организациями для получения названия;
- специфичные WHERE (фильтры, права доступа);
- разные сортировки.

Генерация такого SQL потребовала бы конструктора запросов, что сложнее
и менее читаемо, чем явный SQL.

### Карточки индивидуальные

Причина: карточки — бизнес-интерфейс. У Customer есть выбор организации,
у Product — единица измерения, у Organization — API Key. Общий шаблон
карточки привёл бы к десятку условий (`if.HasOrg`, `if.HasUnit`),
которые сложнее, чем отдельные файлы.

### Нет общего Store / CRUD

Причина: бизнес-логика Save разная.

- Customer проверяет существование организации.
- Organization генерирует API Key.
- Product пока простой — но может появиться проверка unit,
  уникальности имени в рамках организации, etc.

Общий CRUD — это ORM-лайт, который хорошо работает для CRUD без логики
и плохо — когда логика появляется.

### Нет генерации INSERT / UPDATE / SELECT

Причина: см. «SQL остался ручным». Кроме того, генерация INSERT/UPDATE
требует знания, какие поля изменять, а какие — нет (например,
`created_at` нельзя трогать при UPDATE). Это добавляет complexity без
существенной выгоды для проекта с 5–10 справочниками.

## Что изменить перед переносом Customers / Organizations

1. **Добавить второй RowAction** (например, «Удалить») — проверить,
   что шаблон и `ListPage` справляются.

2. ~~**Решить проблему OrganizationName.**~~ **Решено.** Поле
   `OrganizationName` добавлено в модель с `readonly:"true"`.
   Store заполняет его через JOIN в `Get()`/`List()`.
   `Save()` не знает о нём. Handler фильтрует колонку при показе
   внутри организации (см. `app/products.go`).

3. **Оценить Search.** Пока поиск не реализован нигде.
   `SearchFields()` возвращает поля, но Store должен принимать
   search-параметр и строить `WHERE ... LIKE`. Можно реализовать
   хелпер в `entity` или оставить ручным.

4. **Оценить Pagination.** Пока списки маленькие. Когда понадобится
   пагинация — придётся менять Store, ListPage и шаблон.

## UI Contracts

Доменные модели могут реализовывать интерфейсы пользовательского
интерфейса, если они предоставляют информацию о собственном
представлении или навигации.

Эти интерфейсы являются **необязательными** и реализуются **неявно**
в соответствии с модель Go: доменный пакет не импортирует UI-пакеты.

| Интерфейс | Назначение | Пакет |
|---|---|---|
| `display.Values` | Отображаемые значения полей | `internal/ui/display` |
| `navigation.Routable` | Канонический URL объекта | `internal/ui/navigation` |

### display.Values

Пакет `internal/ui/display` определяет интерфейс:

```go
type Values interface {
    DisplayValue(name string) (string, error)
}
```

Модель (например, `products.Product`) реализует его без импорта `display`.
Go удовлетворяет интерфейс неявно. Это позволяет:

- держать доменный пакет (`products`) свободным от UI-зависимостей;
- форматировать значения в одном месте (булевы → текст, даты → локализованный
  формат);
- передавать модель напрямую в код отображения без промежуточного
  преобразования.

`DisplayValue(name)` принимает `GoName` поля (из Descriptor) и возвращает
строку для UI. Для неизвестных полей возвращает ошибку.

В будущем `DisplayValue` может быть заменён на `FieldValue(name) any`
(сырое значение) + отдельный слой форматирования, но пока ручной
`switch` достаточен.

### navigation.Routable

Пакет `internal/ui/navigation` определяет интерфейс:

```go
type Routable interface {
    URL() string
}
```

Модель (например, `products.Product`) реализует его, возвращая
канонический URL объекта:

```go
func (p Product) URL() string {
    return "/organizations/" + p.OrganizationID + "/products/" + p.ID
}
```

URL используется UI при построении списков: handler записывает
`p.URL()` в `Row.URL`. Если `Row.URL` непустой, шаблон списка
использует его вместо `RowAction.BaseURL + ID`.

Это позволяет единообразно строить ссылки для страниц, где
родительский идентификатор одинаков для всех строк (например,
товары в рамках одной организации) и где он свой у каждой
строки (глобальный список товаров).

## Границы Descriptor

`entity.Descriptor` предназначен **исключительно для описания представления
сущности** (UI metadata).

Он **не используется** для:

- генерации SQL-запросов (`SELECT`, `INSERT`, `UPDATE`, `DELETE`, `JOIN`);
- генерации `Store`, `Handler` или другого прикладного кода;
- генерации CRUD-операций;
- генерации HTML-шаблонов;
- генерации API или Integration endpoints;
- валидации данных;
- проверки прав доступа;
- реализации бизнес-логики;
- принятия бизнес-решений.

`Descriptor` предоставляет только метаданные о полях сущности (имя, подпись,
порядок отображения и участие в представлении списка/поиске). Все решения
о том, **как** использовать эти данные, принимаются явным кодом обработчиков
и шаблонов.

Такое ограничение является сознательным архитектурным решением. Оно
предотвращает постепенное превращение `Descriptor` в ORM или генератор CRUD
и сохраняет бизнес-логику полностью явной и читаемой.

## Заключение

Архитектура с `internal/entity` + ручной SQL + индивидуальные карточки
представляет собой компромисс между автоматизацией и явностью.
Решение автоматизирует только то, что ДЕЙСТВИТЕЛЬНО повторяется
(описание полей, шаблон списка), и оставляет явным то, что специфично
(SQL, карточки, бизнес-логика).

Этот подход рекомендуется к распространению на Customers и Organizations
после интеграции и стабилизации.
