# Orders Server — Функциональные требования

Версия: 0.1

---

# 1. Назначение

Система предназначена для создания, отправки и просмотра товарных чеков.

Основным устройством пользователя является смартфон.

---

# 2. Основной сценарий работы

После успешной авторизации пользователь попадает на экран списка товарных чеков.

Из списка пользователь может:

- создать новый товарный чек;
- открыть существующий товарный чек;
- выполнить поиск.

После завершения работы с документом пользователь возвращается в список товарных чеков.

---

# 3. Товарный чек

Документ содержит следующие реквизиты:

- Клиент
- Дата
- Статус

Документ содержит табличную часть со строками товаров.

Строка содержит поля:

- Товар
- Количество
- Цена
- Сумма

Итоговая сумма документа вычисляется автоматически как сумма строк.

Количество, цена и сумма строки должны быть больше нуля. Документ нельзя
сохранить без строк: пустой документ (0 строк, `total = 0`) отклоняется.

## Дата и автор документа

Дата документа и автор (пользователь, создавший документ) назначаются
только сервером:

- при создании нового документа (`ID == 0`) дата — текущая дата сервера,
  автор — текущий пользователь сессии; значения `date` и `user_id` из
  POST игнорируются;
- дата документа всегда совпадает с датой создания (`created_at`);
- при копировании документа дата и автор исходного документа не
  переносятся: новый документ получает текущую дату и текущего
  пользователя;
- при редактировании существующего документа (`ID != 0`) дата и автор не
  меняются.

Клиент не является источником истины: подмена `date`/`user_id` в POST не
влияет на сохранённый документ.

## Файлы документа

К документу могут быть прикреплены PDF-файлы. Файлы доступны для
просмотра во всех статусах, кроме «Отменен»:

- у отменённого документа кнопка «Файлы» в списке не показывается;
- в карточке просмотра имена файлов видны, но не открываются;
- прямой запрос файлов отменённого документа (`/receipts/{id}/files` и
  `/receipts/{id}/files/{fileID}`) возвращает `403 Forbidden`.

## Список документов и отбор

Список содержит колонку «Пользователь» — логин создателя документа.
В панели отбора доступен отбор по пользователю-создателю.

# 4. Правила расчета

При изменении количества автоматически пересчитывается сумма строки.

При изменении цены автоматически пересчитывается сумма строки.

При изменении суммы автоматически пересчитывается цена.

После любого изменения строк автоматически пересчитывается итог документа.

**Точность числовых значений.**

- **Количество — максимум 3 знака после запятой.**
  - Ввод: `step="0.001"`; третья и все последующие цифры при вводе
    урезаются (значение поля `1.2345` → `1.234`).
  - Сервер: значение округляется `round3` (`1.2345` → `1.235`).
- **Цена и сумма строки — максимум 2 знака после запятой.**
  - Ввод: `step="0.01"`; третий знак при вводе урезается (`2.3456` → `2.34`).
  - Сервер: значение округляется `round2` (`2.3456` → `2.35`).
- **Итог документа — максимум 2 знака.**
- Все вычисления округляются на каждом шаге:
  - сумма строки: `amount = round2(количество × цена)`;
  - цена (при изменении суммы): `price = round2(сумма / количество)`;
  - итог: сумма **округлённых `amount`** строк, `total = round2(total + amount)`.
- Сумма строки (`amount`) — самостоятельное доверенное значение:
  введённая сумма сохраняется (после `round2`) и **не заменяется** расчётным
  `количество × цена`. Если пользователь меняет сумму, цена пересчитывается из
  неё, но сам `amount` остаётся как введён.
- **Урезание относится только к пользовательскому вводу**; серверная
  нормализация полученного значения выполняется округлением.
- Сервер — источник истины: `ReceiptSave` повторяет ту же нормализацию
  (`round3` для `quantity`, `round2` для `price` и `amount`) перед
  сохранением и считает итог из округлённых `amount`. Браузер не является
  источником истины.
- Серверная проверка отклоняет строки с нулевым или отрицательным
  количеством, ценой или суммой, а также документ без строк. Проверка
  действует для обоих способов правки строки — через модалку и прямо
  в таблице.
- Инвариант домена: после сохранения `quantity` имеет точность не более 3
  знаков после запятой, а `price`, `amount` и `receipt.total` — не более 2.
  Ограничение на уровне SQLite (REAL) не добавляется.

Из-за округления цены до двух знаков `amount` может не быть математически
равным `quantity × price` — это допустимо и ожидаемо.

# 5. Статусы документа

Документ может находиться в одном из следующих состояний:

- Создан
- Просрочен (производное состояние, в БД не хранится)
- Отправлен
- Принят
- Отменен
- Обработан
- Завершен

## Создан

Документ доступен для:

- редактирования;
- удаления;
- отправки;
- отмены пользователем.

---

## Просрочен

Производное состояние отображения, а не самостоятельный статус.
Появляется поверх `Создан`, если возраст документа достиг 24 часов.

Особенности:

- в базе не хранится: в `receipts.status` остаётся `Создан`;
- из 1С не принимается;
- как только документ перестаёт быть `Создан`, просрочка исчезает.

---

## Отправлен

Статус устанавливается пользователем.

После отправки:

- документ становится доступен только для просмотра;
- редактирование запрещено;
- удаление запрещено;
- отмена пользователем запрещена.

Дальнейшее изменение статуса выполняется только через API.

---

## Принят

Статус устанавливается только через API.

Документ доступен только для просмотра.

---

## Отменен

Статус может быть установлен:

- пользователем, если документ не был отправлен;
- внешней системой через API после отправки.

Документ доступен только для просмотра.

К документу может быть прикреплен один или несколько PDF-файлов.

Изменение действия (Удалить/Изменить) запрещено.

---

## Обработан

Статус устанавливается только через API.

Документ доступен только для просмотра.

К документу может быть прикреплен один или несколько PDF-файлов.

---

## Завершен

Статус устанавливается только через API.

Документ доступен только для просмотра.

---

## Цвет статуса

Цвет строки в списке документов вычисляется Orders автоматически
по статусу. 1С цвет не передаёт; `status_color` из API и приложения
исключён.

| Статус    | Цвет      |
| --------- | --------- |
| Создан    | нет       |
| Просрочен | `#FFFF00` |
| Отправлен | `#00BFFF` |
| Принят    | `#FFA500` |
| Отменен   | `#FF0000` |
| Обработан | `#00FF7F` |
| Завершен  | `#006400` |

---

# 6. Переходы между статусами

Допустимы следующие переходы:

```
Создан
  └─ 24 часа → Просрочен (только отображение)

Создан/Просрочен
  └─ отправка → Отправлен

Отправлен
  └─ 1С → Принят / Отменен / Обработан / Завершен
```

Кроме того, до отправки допускается отмена пользователем:

Создан → Отменен

Другие переходы не допускаются.

---

# 7. Интеграция с 1С

Обмен с 1С всегда инициируется системой 1С. Orders не выполняет
исходящих запросов к 1С.

## 7.1. Доступность документа для синхронизации

Документ считается доступным для получения 1С, если одновременно:

- `SentAt IS NOT NULL` (документ опубликован пользователем);
- `UUID IS NULL` (ещё не получен 1С).

## 7.2. Жизненный цикл синхронизации

1. Пользователь создаёт и редактирует документ.
2. Пользователь нажимает «Отправить» → `SentAt = now()`.
3. Документ становится read-only (редактирование и удаление запрещены).
4. 1С запрашивает документы: `WHERE sent_at IS NOT NULL AND uuid IS NULL`.
5. 1С вызывает `Synchronize()`, передавая UUID и статус.
6. Документ получает UUID и перестаёт быть доступным для выгрузки.
7. Дальнейшее изменение статуса выполняется 1С через `Synchronize()`.

## 7.3. Разделение ответственности

Orders:
- создание и редактирование документа;
- публикация документа (установка `SentAt`);
- вычисление цвета строки из фиксированного статуса
  (а также производного состояния «Просрочен»).

1С:
- получение опубликованных документов;
- присвоение UUID;
- управление статусом (из фиксированного списка).

# 8. Справочник товаров

Поля:

- UUID
- Наименование
- Единица измерения
- Активный

В новых документах допускается выбор только активных товаров.

Если товар использовался ранее, он продолжает отображаться в существующих документах независимо от признака активности.

Создание, изменение и удаление товаров выполняется только через API.

---

# 9. Справочник контрагентов

Поля:

- UUID
- Наименование
- Активный

В новых документах допускается выбор только активных контрагентов.

Если контрагент использовался ранее, он продолжает отображаться в существующих документах независимо от признака активности.

Создание, изменение и удаление контрагентов выполняется только через API.

---

# 10. PDF-файлы

PDF-файлы добавляются и обновляются только через API.

Пользователь может:

- просматривать список PDF;
- открывать PDF.

Пользователь не может:

- добавлять PDF;
- изменять PDF;
- удалять PDF.

PDF принадлежат внешней системе; Orders Server хранит их и отдаёт
пользователю для просмотра.

- по контрагенту;

# 12. Ограничения

Редактирование товарного чека допускается только в статусе **Создан**.

Во всех остальных статусах документ доступен только для просмотра.

Изменение статуса документа после отправки выполняется только через API.

---

# 13. Требования к интерфейсу

Интерфейс проектируется по принципу Mobile First.

Основным рабочим экраном является список товарных чеков.

Интерфейс должен обеспечивать работу одной рукой.

Количество переходов между экранами должно быть минимальным.

Все действия должны выполняться без горизонтальной прокрутки.

---

# 14. Жизненный цикл документа

Документы (чеки, накладные и т.д.) являются агрегатами.

- До успешного прохождения валидации агрегат существует **только в интерфейсе
  пользователя** и не записывается в базу данных.
- В БД сохраняется только полностью сформированный документ, прошедший
  бизнес-валидацию.

---

# 15. Метаданные полей

Поведение полей описывается метаданными (`Visible`, `ReadOnly`, `Required`,
`DefaultValue`, `Validator`).

- Метаданные являются единым источником информации для UI и сервера.
- Ошибки валидации привязываются к конкретным полям.
- Документы дополнительно проходят проверку агрегата (наличие организации,
  контрагента, строк).

---

# 16. Обработка ошибок валидации

- При ошибке валидации пользователь остаётся на текущей форме.
- Все введённые данные сохраняются.
- Поля с ошибками выделяются визуально.
- Сообщения об ошибках отображаются рядом с полем или в общей области ошибок
  документа.
- Повторный ввод выполняется без потери данных.
